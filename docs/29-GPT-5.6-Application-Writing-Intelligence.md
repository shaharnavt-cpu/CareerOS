## Provider boundary

The application-writing provider sits after CareerOS has compiled, filtered,
ranked, and selected approved evidence, and before a generated version is
persisted:

```text
target + ordered application questions + 2-4 selected compiled memories
  + approved supporting context
  -> ApplicationWritingInput
  -> local-deterministic or OpenAI provider
  -> ApplicationWritingOutput
  -> narrow, recorded pre-persistence sanitization
  -> deterministic claim, quality, and privacy validation
  -> immutable application-package version
```

Provider selection is server-owned through `APPLICATION_WRITER_PROVIDER`.
`local-deterministic` is the offline default and `openai` is the live option.
The typed input/output boundary is intentionally provider-neutral so an
Anthropic adapter can be added later without moving factual policy into the
package service. API keys never enter provider input, responses, persisted
versions, or the frontend.

The provider receives only the minimum relevant context: the target, explicit
ordered application questions, grouped requirements, 2-4 selected compiled
profiles, relevant approved enrichment and proof artifacts, strategy-only
outcome signals, prohibited claims, missing proof, requested tone/length, and
schema metadata. Proposed, rejected, archived, duplicate, foreign, unrelated,
and raw uploaded material is excluded.

## Intelligence pipeline and ownership

Generation is an explicit pipeline:

1. understand the job semantically and group its responsibilities and
   requirements;
2. rank approved memory for relevance, evidence strength, specificity,
   confidence, proof availability, recency, and redundancy;
3. recommend and select the best 2-4 memories by default;
4. plan supported, partial, unsupported, and prohibited claims;
5. draft positioning, concise resume bullets, a natural cover letter, direct
   answers keyed to supplied application questions, reviewer questions, and
   proof suggestions;
6. critique genericness, repetition, mechanics, technical overload, relevance,
   and 30-second recruiter readability;
7. optionally rewrite while preserving evidence references; and
8. deterministically validate every factual claim before persistence.

CareerOS owns truth, provenance, exclusions, memory boundaries, validation,
readiness, and persistence. A writing provider may interpret relevance and
improve strategy, phrasing, concision, naturalness, and recruiter readability;
it may not create facts. Provider failure never deletes an existing version or
persists an empty one.

Broad concepts use semantic groups: analytics, reporting/communication,
modeling, data quality, and research/problem solving can match equivalent
approved proof. Concrete technologies continue to require direct evidence,
including Python, SQL, cloud platforms, Docker, Kubernetes, deployment, LLMs,
RAG, agents, Tableau, and Power BI.

## Sprint 14.1.1 claim contract

### Immutable evidence ledger and claim surfaces

The server gives the provider an explicit ledger of immutable approved evidence
atoms. Each atom has a stable `evidence_atom_id` and `approved_claim_id`, its
canonical-memory association, optional enrichment/proof-artifact IDs, source
evidence references, a short factual statement, supported tools and methods,
an optional structured outcome, allowed certainty, support type, and prohibited
expansions. Target-context and inferred-framing atoms stay distinguishable from
direct proof.

Every candidate-facing field has exactly one structured `candidate_claims`
record containing the exact rendered text, field path, claim type, evidence-atom
IDs, tools claimed, structured outcome when present, and certainty. Candidate
claim surfaces are the positioning summary, each resume bullet, each classified
cover-letter section, and each application answer. The assembled cover-letter
text must match those classified sections.

Job understanding, requirement coverage, unsupported requirements, missing-
proof and do-not-claim guidance, reviewer questions, proof suggestions,
strategy/critic/quality notes, target-job tool lists, and validation metadata
are analysis-only. An unsupported tool may appear there as a gap or warning; it
is not candidate experience. If an analysis path is incorrectly supplied as a
candidate claim, validation rejects it with
`ANALYSIS_FIELD_MISCLASSIFIED_AS_CLAIM`.

### Structured outcomes, tools, and pre-persistence repair

Outcome support is represented as evidence source, action, object, result,
qualifier, certainty, and optional metric. Harmless grammatical paraphrasing is
allowed when those semantic components and the project association stay the
same. Changed objects, actions, results, metrics, qualifiers, certainty, source,
or cross-project support remain deterministic failures. Concrete tools and
deployment language require a cited direct atom that explicitly lists the
capability; target wording and analysis-only gap text never supply that proof.

After structured parsing and before persistence, CareerOS classifies the known
candidate surfaces, checks claim metadata and evidence references, and supports
one deliberately narrow repair type: it may remove a separable trailing
unsupported-warning sentence without changing the central factual proposition.
Each such repair is recorded in `validation_metadata.repairs` with its code,
section, field path, normalized phrase, evidence IDs, and action. A central or
otherwise material unsupported claim fails the whole new version; it is never
silently rewritten, and any prior immutable package version remains intact.

### Privacy-safe validation diagnostics

Claim-contract failures expose only the stable validation rule/code, output
section, field path, normalized disputed phrase, referenced evidence IDs,
expected evidence category, and whether the field was `user-facing` or
`analysis-only`. Stable codes include `OUTCOME_OBJECT_MISMATCH`,
`UNSUPPORTED_CONCRETE_TOOL`, `UNSUPPORTED_DEPLOYMENT_CLAIM`,
`ANALYSIS_FIELD_MISCLASSIFIED_AS_CLAIM`, `UNKNOWN_EVIDENCE_REFERENCE`, and
`CROSS_MEMORY_CLAIM_LEAKAGE`. Diagnostics never print the API key,
authorization headers, full prompt, private career context, full provider
response, generated private claim text, or hidden reasoning.

## Sprint 14.1.2 application question/answer contract

### Explicit questions and exact answer mapping

The package persists an ordered `application_questions` list and passes it to
both providers. Each question contains `question_id`, `question_text`,
`required`, optional `maximum_length`, optional `response_type`, and
`relevant_target_requirement_ids` where applicable. The provider does not infer
a count and does not invent generic questions to fill a quota.

Each answer contains `question_id`, `answer`, `evidence_reference_ids`,
`evidence_atom_ids`, `tools_claimed`, `outcome_claimed`, `certainty`, and
`validation_metadata`. The strict schema validates item shape; deterministic
input-aware validation then enforces exactly one non-empty answer for every
required question, known and unique IDs, and input order. Optional unanswered
questions may be omitted. Zero questions permits, and requires, zero snippets.
Answer count derives solely from the supplied list; no global minimum applies.

Structural failures use `MISSING_REQUIRED_APPLICATION_ANSWER`,
`DUPLICATE_APPLICATION_ANSWER`, `UNKNOWN_APPLICATION_QUESTION_ID`,
`EMPTY_APPLICATION_ANSWER`, or `APPLICATION_ANSWER_ORDER_MISMATCH`. A missing
answer is a structural contract problem, not a factual hallucination.

### Targeted answer-only repair

A missing required answer may consume the one structured repair attempt. The
repair request contains only the missing question IDs/text, already valid
package sections, relevant evidence atoms, prohibited claims, and the strict
answer schema. It cannot ask the model to regenerate valid resume bullets or
cover-letter sections. Only returned repaired answers are merged; CareerOS then
revalidates the entire package. A failed repair preserves the previous immutable
version.

Answer-only repair does not bypass factual validation. Every original or
repaired answer remains a candidate-facing claim with required evidence and
claim metadata; unsupported tools, outcomes, unknown references, and cross-
memory leakage remain blocked. The narrow Sprint 14.1.1 sanitizer and the
`private`/`demo-shared` data policy are unchanged and still run before
persistence.

## OpenAI Responses API adapter

The OpenAI adapter uses the Responses API with a strict JSON schema for
`ApplicationWritingOutput`, `store=false`, server-side credentials, bounded
input characters and output tokens, a configurable timeout, and configurable
reasoning effort. The SDK client disables implicit HTTP retries so the adapter's
single optional bounded structured-repair attempt is the complete retry budget.
The cost-safe default is one `gpt-5.6-terra` structured generation request.
`gpt-5.6-sol` is reserved for an explicitly enabled recruiter review/rewrite
pass and is disabled by default.

The adapter distinguishes missing key/model, authentication, billing,
rate-limit, timeout, refusal, malformed structured output, and other provider
or network errors. It permits at most one bounded structured-output or missing-
answer repair attempt and does not blindly retry authentication, billing, or
rate-limit failures. If the optional Sol review fails, the valid Terra result
is retained with a review-unavailable note. Deterministic validation runs after
provider output and again
after any review rewrite.

When available, a saved version records safe operational metadata: provider,
model, request ID, latency, token counts, and whether review ran. It never
records the key, authorization headers, complete private context, full raw
prompts, or hidden reasoning.

## Writing and review experience

Both providers produce a recruiter-readable narrative rather than concatenated
database fields. Cover letters target roughly 250-400 words in 3-4 substantive
paragraphs, use 2-3 strong proof points, and avoid internal phrases such as
"approved memory" and mechanical wording such as "focused on the project tested
whether." Resume bullets favor one 20-35 word idea with an action, object, and
purpose/result. Each supplied-question answer responds immediately in first
person and stays concise.

The workspace distinguishes recommended from selected memories, groups
requirement coverage and warnings, groups and deduplicates evidence by canonical
memory, shows a concise quality review, and identifies the provider/model.
Existing edit/copy controls, immutable versions, `READY`, archive/restore, and
stale-output protections remain unchanged.

## Configuration without an OpenAI key

Copy `.env.example` to the appropriate untracked local environment file and
keep these defaults:

```dotenv
APPLICATION_WRITER_PROVIDER=local-deterministic
APPLICATION_WRITER_DATA_POLICY=private
OPENAI_API_KEY=
OPENAI_APPLICATION_ENABLE_REVIEW_PASS=false
RUN_LIVE_OPENAI_TESTS=false
```

Local generation and the complete non-live test suite require no API key.

## Cost and privacy controls

- No call occurs on page load, refresh, viewing, copying, editing, or package
  history access; generation/regeneration is explicit.
- The default live path is one Terra call, with Sol disabled.
- Context is reduced to 2-4 relevant compiled memories and strict size limits.
- Raw documents and unrelated memory are not sent when compiled proof suffices.
- `store=false` is mandatory and full private prompts are not logged.
- `private` minimizes normal approved user context; `demo-shared` accepts only
  seeded or explicitly marked fictional/redacted profiles and is required for
  shared Build Week project testing.
